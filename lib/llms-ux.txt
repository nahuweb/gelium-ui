# Gelium UI — UX decision pack (for agents)

First read `skills/00-agent-routing.md`. It is the canonical outcome-first
route selector; this file defines downstream Gelium UX decisions.

Human: /docs/agent-workflow /docs/screens /docs/feedback /docs/journeys /docs/data-display /docs/patterns /docs/density /docs/motion /docs/content-style /docs/ui-definition-of-done /docs/section-references
Ethos: server HTML + gelium-ui tokens/themes; sourced criteria; JS optional. NOT free-form aesthetic redesign.

## MUST before generating UI

0. ROUTE: direct-exempt | delegated-direct | design-gated | escalate | full-sdd.
   Small understood
   fixes stay direct; new screens, flows, and substantial redesigns are a
   design-gated route; use OpenSpec only when cross-cutting ambiguity needs
   durable planning.
0a. INTENT MODE: new-product | redesign | visual-migration. Existing UI is evidence,
   not authority; visual-migration is explicit opt-in, not an inference.
1. SURFACE mode: Operate | Read | Persuade | Experience (Operate default for tools)

2. USER JOB: one sentence
3. SCREEN TYPE: hub | list | detail | form | confirm | settings | queue | result
4. ONE PRIMARY ACTION
5. JOURNEY-* if multi-step; DATA-* if collection
6. STATES + FEED-*
7. CONTROLS: forms + choose-the-right-control
8. SERVER: GET read; POST+303; 422+X-Gelium-Validation
9. THEME: theme-* on html (no one-off hex chrome)
10. NARROW: stack; min-width:0; no overflow-x:hidden on body
11. DoD: /docs/ui-definition-of-done
12. Read consumer PRODUCT.md + DESIGN.md when present. If either is absent, run the plain-language brief below before choosing screen architecture.
13. SECTION CONTRACTS: define each major region by purpose before choosing components.
14. VISUAL + INTERACTION DIRECTION: choose Gelium theme, visual recipe/skin,
registered behavior patterns, copy/locales, and MEDIA-* references before Build.

## PLAIN-LANGUAGE BRIEF

Do not require product or design vocabulary from the user. Ask one question at a time:

1. What are you trying to build or improve?
2. Who will use it, and when?
3. What should that person be able to accomplish?
4. What is definitely out of scope for this slice?

Turn the answers into a draft PRODUCT.md/DESIGN.md, read back the interpretation, and ask only conditional follow-ups (roles, objects/states, URLs, navigation, references, or success criteria). Accept `Unknown`, `To decide`, and `N/A` with a reason. Record assumptions and open decisions; never fill missing product intent with invented SaaS patterns.

Before markup, the brief must establish a user job, a surface mode or an explicit unresolved choice, a visual direction or an explicit unresolved choice, and the scope boundary. For `redesign`, it must also record a current-state audit; for `visual-migration`, it must record the preserved UX/server contracts. Stop only when an unresolved decision would change page/flow architecture.

For design-gated work, use
`ROUTE → ORIENT → PLAN → ARCHITECT → APPROVE → BUILD → AUDIT → RELEASE`.
This sequence is required for design-gated work. Prebuild needs a brief,
architecture packet, approval/exemption, and a prebuild criteria plan. Show
the buildable wireframe in the conversation and wait; do not start markup
because the user asked to make the page or said continua. The wireframe must
show the global shell (header/navigation and footer, including unchanged shell
bands), ordered purpose-bound regions, one primary action, WIDE and NARROW
layouts, states/recovery, and technical/no-JS annotations. An unresolved shell
decision blocks approval. Use the structural ASCII protocol in
`skills/12-wireframe-approval.md`; do not treat generic cards as sections.
Audit, after a candidate exists, records rendered audit evidence for
wide/narrow, class-routed themes, states, no-JS, detector, and applicable
checks. After the structural intent wireframe, run a Visual + Interaction
Direction pass for the Gelium theme/recipe/skin, registered behaviors,
copy/locales, and media. Then produce the buildable wireframe and wait for
approval. Start from `skills/templates/gate-ledger.md` and
`skills/templates/wireframe-approval-packet.md`; attestations are evidence, not
proof of cognitive reading or delivery authority.

## WORKFLOW (WF-*)

| ID | Do | Don't |
|---|---|---|
| WF-BRIEF | plain-language job, audience, outcome, scope, and intent mode | skip questions, require jargon, or invent design decisions |
| WF-CURRENT-STATE | for redesign/migration, audit preserve/improve/remove/unknown with evidence | treat an existing screen as authoritative |
| WF-SHAPE | list SCREEN/JOURNEY/DATA/FEED ids and section purposes | write markup in shape |
| WF-DIRECTION | select Gelium theme/recipe/skin, registered behaviors, copy/locales, and MEDIA-* references | defer layout-affecting behavior or media until Build |

| WF-ARCH | apply ARCH-PRODUCT → ARCH-PAGE → ARCH-SECTION; outline major regions and complete SECTION-CONTRACT before components | use cards, spacing, or CSS to invent a missing section purpose |
| WF-BUILD | partials + server; page shells compose registered components | invent parallel design system or hand-roll nav/page shells |
| WF-AUDIT | DoD + WF-SECTION-AUDIT + bash node_modules/@gelium/ui/scripts/ux-detect.sh | claim pass without checks |
| WF-SECTION-AUDIT | five-second scan, action competition, revelation/recovery, then rendered-HTML evidence | call an uncontracted region or hover/JS-only recovery acceptable |
| WF-POLISH | theme/spacing/copy one pass | redesign under polish |
| WF-HARDEN | empty/error/edge | happy-path only |
| WF-ONBOARD | first-run empty CTA | blank first screen |

## PAGE + SECTION ARCHITECTURE

| ID | Rule |
|---|---|
| ARCH-PRODUCT | Record audience, user job, outcome, non-goal, and relevant lifecycle/event consequences. |
| ARCH-PAGE | Record URL, SURFACE/SCREEN, one primary action, JOURNEY/DATA/FEED IDs, chrome, and server/no-JS contract. |
| ARCH-SECTION | Give every major region one purpose-bound section contract before components. |
| ARCH-COMPONENTS | Compose registered semantic primitives only after section purpose is known. |
| ARCH-TOKENS | Express approved relationships through existing semantic tokens and class-routed skins. |
| SECTION-CONTRACT | Record purpose, audience/moment, input, output/next move, hierarchy, action policy, revelation, composition, state/recovery, boundary/rhythm, accessibility/content, and rendered evidence. |
| SECTION-HIERARCHY | DOM order is entry → primary → supporting → recovery; card anatomy is not automatically a section. |
| SECTION-ACTION | One page primary action; section-local actions remain secondary unless the section owns that declared action. |
| SECTION-REVELATION | Initial scan shows identity and task-critical state; conditional state is server-rendered; optional depth uses native disclosure. |
| SECTION-RECOVERY | Every applicable data/action section names rest/loading/empty/error/success and a no-JS way forward. |

Details: `skills/10-page-section-architecture.md` (normative) and
`/docs/page-section-architecture` (human companion). Worked applications use
existing `/recipes/public-feed` and `/recipes/rich-article` routes only.

## ANTI-SLOP (Gelium-aware)

Avoid: nested cards for simple forms; stock purple-blue heroes; icon-tile above every H1; gray on saturated fills; bounce motion; bolder-for-its-own-sake on Operate tables; new font per feature; layout tables for non-data.
OK: Material/Basecoat/Neubrutalism stacks from theme; brand fonts if DESIGN.md says so.

## NAV / DENSITY / MOTION

Nav: side 1–3 levels; bar 3–5 peers; tabs=same object; breadcrumb depth≥2.
Density: comfortable|cozy|compact — one per surface; keep --ui-touch-target.
Motion: MOTION-NONE default; honor prefers-reduced-motion.

## FOUNDATIONS (human docs)

| ID | Rule |
|---|---|
| DOC-TYPE | Use `/docs/typography`; choose a `--ui-type-*` role, preserve its size/weight/line-height, and keep prose near 65ch. |
| DOC-SPACE | Use `/docs/spacing`; compose with `--ui-space-1/2/3/4/6/8`, smaller inside groups and larger between groups. |
| DOC-COLOR | Use `/docs/colors`; consume semantic `--ui-color-*` pairs, test focus/status in light and dark, and never use color alone. |
| TYPE-ROLE | Theme overrides decomposed type tokens; consumers keep the alias. |
| SPACE-SCALE | No feature-specific spacing scale; use the core scale and keep touch targets at `--ui-touch-target`. |
| COLOR-FOCUS | Keep `--ui-color-focus-ring`, `--ui-focus-thickness`, and `--ui-focus-offset` visible on `:focus-visible`. |

## MEDIA (server-rendered, native-first)

| ID | Rule |
|---|---|
| MEDIA-IMAGE | Informative images require meaningful `alt`, trustworthy intrinsic `width`/`height` when available, and lazy loading below the fold. If dimensions are unknown, do not fabricate them: preserve alt, safe responsive containment, and recovery, then record `media-metadata-unknown` or `pass-with-escalation` in the audit. |
| MEDIA-RESPONSIVE | Use real `srcset`/`sizes` variants or a single source; never invent variants; preserve aspect-ratio fallback. |
| MEDIA-AUDIO | Use native `audio[controls]`, typed sources, fallback text, and link an optional readable transcript. |
| MEDIA-CAPTIONS | Video with meaningful audio gets a captions track; captions and transcript serve different jobs. |
| MEDIA-EMBED | Render external iframes only across an explicit allowlist + consent boundary; otherwise show a canonical fallback. |
| MEDIA-STATES | Reserve space for loading; provide recovery for error; explain empty media. |

## REFERENCE-SELECTION
After SURFACE/SCREEN and before ARCH/wireframe, perform a semantic match against
published section references and the component registry. A matching need makes
that reference input mandatory when available; no match is not an error.
Before filtering, fish the reference for visible affordances and responsive
choices (detail entry, icon-versus-text actions, search, account/menu, shell,
media, and recovery). Also audit identity/account grouping, constant state,
and visibility semantics: do not duplicate shell destinations, repeat a badge
that is true for every row, or expose visibility where the surface is public-only.
The shell must also apply first-plane priority and progressive disclosure: keep
primary navigation visible, group low-frequency settings/logout behind a named
account control when safe, and compare reference diversity before choosing a
chrome model.
Do not omit a candidate because it is absent from the current contract; classify it as existing contract, B, C, fork, or rejected.
Fail-open if there is no browser, the source is blocked, or the reference cannot
be verified. Record matched IDs (or the no-match reason) in the plan/G5 packet.
Use references for structure and decisions, never copied skin, branding, assets,
claims, screenshots, or motion. Apply the product filter before A/B/C.
Section references cover page composition; component references cover local
behavior and states. Gelium contracts remain authoritative.

## SECTION REFERENCES
Section references: `/docs/section-references` when the docs site is available; npm-only consumers use `references/catalog.json` and `references/section-references/*.md`.
Cite official URLs. Block map or our crop. Gelium remake must exist. Not a moodboard.

| ID | Rule |
|---|---|
| REF-ARTICLE | Read/detail article. On-page Gelium reconstruction of the cited structure, not `/recipes/rich-article`. |
| REF-404 | 404/detail reference. Reconstruct the cited not-found structure with Gelium's `ui-error-state`, not a screenshot or unrelated recipe. |
| REF-AUTH | Auth/form reference. Reconstruct registration with native labeled fields, consent, one primary submit, recovery, and a server-side 422 story; never claim an unregistered auth route exists. |
| REF-FAQ | FAQ/detail reference. Reconstruct the cited pricing FAQ with native `details`/`summary` disclosure and one decision action; keep answers and commercial claims owned and current. |
| REF-HERO | Persuade/hub reference. Reconstruct the cited landing hero with `ui-hero`, one page `h1` supplied by the page, short context, one primary action, and no copied logo, asset, gradient, or motion. |
| REF-PRICING | Pricing/detail reference. Reconstruct plan comparison with a mobile-safe `ui-data-table` or semantic cards, one primary CTA, explicit billing basis, and no invented commercial claims. |

## SEO / AEO BOUNDARY

One primary answer per page, answer-first lead, descriptive headings, and visible sources for sourced claims. `/llms.txt` and `/llms-ux.txt` are discovery aids, not ranking guarantees. The library owns semantic markup and media; the docs site owns Gelium metadata, canonical/robots/sitemap, social tags, and JSON-LD; consumers own BASE_URL/domain, brand, content facts, authors/dates, and social assets. Docs/blog may be indexable; recipes, demos, examples, and stateful surfaces stay noindex and out of the sitemap.
